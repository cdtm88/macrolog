MacroLog

Product Requirements Document · target framework: GSD · 22 July 2026

1. Project identity

Name: MacroLog

What it is: A single-purpose iOS app that turns a photo or text description of a meal into a macronutrient estimate and writes it to Apple Health, so that Whoop's Journal can auto-populate its nutrition entries. It does one thing: meal in, macros to Health. It deliberately does not track exercise, weight, goals, streaks, or history, because Whoop already owns all of that.

Target user: One person (the author). Whoop 5.0 user who wants macro data feeding Recovery correlations without paying for or tolerating a full nutrition platform.

Core value: Log a meal's macros to Apple Health in seconds, without ads, upsells, or features you did not ask for.

Stage: Greenfield.

2. Success criteria

  • 90% or more of meals logged over a rolling 30-day period, measured as days with at least two entries divided by days elapsed.
  • Whoop Journal pre-fills protein, carbohydrate, and fat values from MacroLog's Health writes without manual entry, verified on 5 consecutive days.
  • Zero data-loss incidents: no user input is ever discarded by an app error or network failure.
  • MyFitnessPal uninstalled and not reinstalled within 30 days of MacroLog going into daily use.

3. Users and primary jobs

JobUser roleNeeded outcome
Log a meal I just atePrimary user, in the moment, often one-handedMacros in Apple Health within seconds, without leaving the meal
Correct an estimate I do not believePrimary user, reviewing before commitAdjust the numbers before they reach Health, or fix them shortly after
See what I have logged todayPrimary user, glancing at phoneRunning total for the day without opening the app

Job one, working perfectly, makes this worth shipping. The other two exist to protect it.

4. Scope

In scope (v1)

  • Photo capture as the default input; text description as an equal-status alternative one tap away.
  • AI estimation of calories, protein, carbohydrates, and fat from either input type.
  • Mandatory review and edit step before any write to Apple Health.
  • Write to Apple Health as an HKCorrelation of type .food, per meal.
  • Today's entry list with edit and delete, both reconciling the corresponding Health sample.
  • Home Screen widget showing today's running totals.

Out of scope (deferred to BACKLOG)

  • Notifications and reminders of any kind. Revisit only if adherence measurably fails.
  • Fibre, sugar, sodium, micronutrients. Whoop's Journal has no entries for them, so they would be written and ignored.
  • Food database, barcode scanning, branded-item lookup.
  • History beyond today, charts, trends, weekly summaries. Whoop is the history view.
  • Goals, targets, streaks, gamification.
  • Exercise, weight, water, or any non-macro tracking.
  • Multi-user, sync, cloud backup, App Store distribution.
  • Apple Watch app.
  • Offline queue with automatic retry. v1 fails loudly and lets the user retry manually.

6. Technical decisions (locked)

IDDecisionRationale
D-01Native iOS, SwiftUI, iOS 18+ minimumHealthKit write requires a native app; no cross-platform route exists. Single-user app, so no reason to support older OS versions.
D-02SwiftData for the local entry storeOnly today's entries plus pending items are stored; SwiftData is the lowest-ceremony persistence for a single model.
D-03Direct calls to the Anthropic API from the app; no backendSingle user, no shared state, no need for a server. Removes an entire deployment surface.
D-04Latest Sonnet model for estimation, with Opus as a fallback if estimate quality proves inadequateSonnet is fast and cheap enough that per-meal latency stays tolerable; escalate only on evidence.
D-05API key in a gitignored configuration fileKeeps the key out of the repository, which is the material risk for a personal unlisted app. Accepted trade-off: the key is present in the compiled binary and is not protected against device-level extraction.
D-06Write calories, protein, carbohydrate, and fat onlyThese are the only macronutrient entries Whoop's Journal reads. Anything else is written and ignored.
D-07One HKCorrelation per meal, not per dayHealthKit sums samples into a daily total for Whoop regardless of granularity; per-meal correlations are legible in the Health app at no extra cost.
D-08Deleting a local entry deletes the Health sampleLeaving the sample means a deleted meal still counts in Whoop's daily total, which silently corrupts the data the app exists to produce.
D-09No notifications in v1; Home Screen widget insteadReducing the cost of logging holds up better over months than nagging about not logging, and avoids dismissal fatigue.
D-10Fail loudly on network and identification errors; no silent guessingA wrong number the user does not know is wrong is worse than a visible failure they can retry.
D-11Timestamp entries at capture, not at review confirmationReview-before-write means capture and confirmation can be hours apart. Confirming a late dinner after midnight would otherwise land it on the wrong day and corrupt the daily total Whoop correlates against.

7. Work units (GSD phases)

One milestone: M1 — Working daily logger. Phases are ordered so that the two highest risks (Whoop not reading the data; the author not sticking with logging) are tested before any polish is built.

01 — health-write-path

Prove that a non-partner app writing macros to Apple Health is picked up by Whoop's Journal pre-fill.

REQ-IDs: HK-01, HK-02, HK-03, HK-04, HK-05, HK-07, SEC-02, TGT-01

Done: A one-button app writes a hardcoded HKCorrelation to Health; the values appear in the Apple Health app with the description visible; the Whoop Journal pre-fills those values on the same day.

Verification procedure (follow exactly; the pre-fill is order-dependent):

  1. Confirm today's Whoop Journal has not already been saved. If it has, the pre-fill prompt will not appear again until tomorrow and the test cannot run today.
  2. Write the test correlation from the app.
  3. Open the Apple Health app and confirm the four values and the description are present, sourced from MacroLog.
  4. Open the Whoop Journal and start a new entry. Confirm the blue "data pre-filled via Apple Health" banner appears and the protein, carbohydrate, and fat values match what was written.
  5. If the banner does not appear, check Whoop's Apple Health permissions before assuming an app-side defect.

02 — estimation-core

Turn a photo or text description into a reviewed, confirmed macro estimate written to Health.

REQ-IDs: CAP-02, CAP-04, EST-01, EST-02, EST-03, EST-04, EST-05, EST-06, EST-07, EST-08, REV-01, REV-02, ENT-06, PERF-03, PERF-04, SEC-01

Done: A photo of a real meal produces four numeric values, presented for review, editable, and written to Health on confirmation, timestamped to capture time. Airplane mode produces an explicit connectivity error with the input preserved. An invalid API key produces a different, correctly-named error. An unidentifiable photo prompts for text rather than guessing. A landscape photo is estimated as reliably as a portrait one.

03 — entry-lifecycle

Persist entries locally and keep the Apple Health record reconciled through edits and deletions.

REQ-IDs: CAP-05, REV-04, HK-06, HK-08, ENT-01, ENT-02, ENT-03, ENT-04, ENT-05, ENT-07, ENT-08, SEC-03, SCALE-01

Done: Today's entries are listed; deleting one removes its Health correlation; editing one leaves exactly one correlation with the new values; force-quitting mid-entry loses nothing; yesterday's written entries are gone from the local store but remain in Health, while an unwritten entry from yesterday survives the purge and can still be completed. An entry captured at 23:55 and confirmed at 00:05 lands on the capture day. Ten entries logged in one day list and total correctly. Revoking Health permission in Settings produces the permissions path, not a generic error.

04 — friction-pass provisional

Remove every avoidable delay and tap between opening the app and a logged meal.

REQ-IDs (starting hypothesis, revise after the adherence checkpoint): CAP-01, CAP-03, REV-03, PERF-01, PERF-02, A11Y-01

Done: Launch lands directly on camera in under 1.5s; submitting returns control in under 200ms with the estimate resolving in the background; a pending review is visible without navigation; the app is fully operable at the largest Dynamic Type size.

05 — today-widget provisional

Surface today's running macro totals on the Home Screen as a passive logging prompt.

REQ-IDs (starting hypothesis, revise after the adherence checkpoint): WID-01, WID-02, WID-03, WID-04

Done: A Home Screen widget shows today's four totals, updates within 60 seconds of a new entry without reopening the app, shows zeros before the first meal, and opens the capture view when tapped.

Adherence checkpoint. Phase 02 is the earliest point at which real meals can be logged daily, in a deliberately unpolished app. Use it for at least a week before starting phase 04. If logging does not hold up there, the failure mode is known cheaply and phases 04 and 05 can be redirected at the actual problem rather than a guessed one. Phases 04 and 05 are therefore marked provisional: their requirements are a starting hypothesis about what friction matters, not committed scope. Expect to rewrite them after the checkpoint, and do not treat unimplemented provisional requirements as failures.

8. Constraints and risks

  • No deadline. Build quality over speed. No scope/timeline tension in this project.
  • Apple Developer account not yet held. $99/year, required before phase 01 can be tested on device for more than seven days. Free provisioning expires weekly, which is unusable for daily logging. This is a hard blocker on the adherence checkpoint, not just on distribution.
  • Author directs, does not write code. All implementation via Claude Code. Requirements are therefore written as observable behaviour, not implementation detail.
  • Top risk: adherence. The app is built and logging does not become habitual. Mitigated by ordering phases so real-world use starts after phase 02, and by choosing a widget over notifications.
  • Second risk: Whoop pickup. Community reports exist of Apple Health nutrition failing to reach Whoop despite correct permissions. Mitigated by making phase 01 a standalone proof before any other work.
  • Third risk: estimate quality on composite dishes. Photo-based estimation of restaurant food, curries, stews, and anything with absorbed oils is materially unreliable. Mitigated by the mandatory review step and by an equal-status text input. Escalation path is D-04 (Opus fallback).
  • Known unknown: whether photo-default survives contact with reality. Photo input was chosen over text default against a recommendation. If review-step corrections become routine, revisit the default.
  • No compliance surface. Single user, no distribution, no third-party data, no PII beyond the author's own meal data.

9. Assumptions

Inferred rather than stated. Correct anything wrong before starting phase 01.

  • Target device is a current iPhone running iOS 18 or later.
  • The app is for personal use only and will never be submitted to the App Store, so App Review constraints, privacy policy, and health-data advertising restrictions do not apply.
  • "Meal" means any eating occasion including snacks; no fixed breakfast/lunch/dinner slots are enforced.
  • API spend is low enough to need no in-app tracking; ENT and EST requirements cover surfacing failures, not monitoring cost. Spend is checked via the Anthropic console if it ever matters.
  • The Anthropic API is called with the vision-capable messages endpoint; no MCP servers or tools are needed.
  • English-language meal descriptions only.
  • Whoop is read-only from this app's perspective; there is no direct Whoop API integration and none is wanted.
  • Day boundaries follow the device's current local time zone. Crossing zones mid-day may shift which day an entry falls on; this is accepted as harmless for a correlation over weeks, and no reconciliation is built.
